# Дорожная карта

Дорожная карта описывает последовательность доказательств, а не заранее выбранные функции. Каждая стадия начинается только после анализа результата предыдущей. Номера GitHub issue отражают историю их создания, поэтому порядок определяется этапами ниже.

## Этап 0. Подготовить 1С-лабораторию в Hermes Workspace

**Рабочая issue:** [#2 — подготовить 1С-лабораторию в Hermes Workspace](https://github.com/Kwentin3/1c-agent-harness/issues/2)

**Результат:** из пустой основной папки Hermes Project Workspace воспроизводимо получается Git-репозиторий, рабочая Linux-среда, нативная платформа 1С и файловый снимок законно доступной smoke-конфигурации.

Hermes предоставляет workspace и исполнительный backend. Проект не создаёт собственную систему workspace: репозиторий располагается в его корне, а закрытые и производные данные — в `.local/` вне Git.

**Гейт:** подтверждены `cwd`, Git-корень, terminal backend и персистентность; платформа запускается пакетно; снимок повторно создаётся без изменения источника; дистрибутивы, базы и секреты не попадают в Git.

## Этап 1. Доказать read-only исследование

**Рабочая issue:** [#1 — доказать read-only исследование незнакомой конфигурации](https://github.com/Kwentin3/1c-agent-harness/issues/1)

**Результат:** агент на репрезентативной выгрузке незнакомой конфигурации отвечает на контрольные технические и предметные вопросы с проверяемыми доказательствами.

Smoke-конфигурация этапа 0 может использоваться для отладки механики, но продуктовая приёмка требует достаточно сложной конфигурации с независимым человеческим эталоном. Baseline сравнивается как минимум с одним готовым контекстным кандидатом.

**Гейт:** выполнены критерии из `docs/evaluation.md`; источник не изменён; решение о зависимостях основано на сравнении, а не на количестве доступных инструментов.

**Статус: принят для «прийти → открыть → понять».** Один SDMS-run дал exact
oracle coverage 45/47 для baseline и 44/47 для indexed candidate, опасных ложных
выводов 0/0. После него основной агент и независимый reviewer отдельно исследовали
тот же frozen snapshot без индексов и пришли к совместимому пониманию назначения,
предметных областей, ключевых объектов, интеграций и статической бизнес-цепочки.
Существенные различия разрешены по XML/BSL, исходный snapshot неизменен. Это
делегированная dual-agent приёмка понимания одной feature-rich конфигурации, а не
экспертная SDMS-, runtime- или cross-configuration гарантия. См.
[`docs/sdms-evaluation.md`](docs/sdms-evaluation.md).

## Этап 2. Определить границу поддержки кастомных и старых конфигураций

**Рабочая issue:** [#3 — определить границу поддержки кастомных и старых конфигураций](https://github.com/Kwentin3/1c-agent-harness/issues/3)

**Результат:** harness проверен на кастомной конфигурации и целевой старой версии платформы. Известно, какие возможности доступны нативно, какие требуют fallback, а какие не поддерживаются.

**Гейт:** опубликована подтверждённая матрица возможностей без обещания «поддерживать всё»; fallback не нарушает доменные контракты; потребность в форке либо доказана, либо отклонена.

**Статус:** кастомная SDMS подтверждена на 8.5.1.1150; точной старой платформы в
workspace нет. Этап не закрыт до появления законного дистрибутива или snapshot,
созданного целевой старой версией; см. [`docs/compatibility.md`](docs/compatibility.md).

## Этап 3. Доказать независимость от кодового агента

**Рабочая issue:** [#4 — доказать независимость от конкретного кодового агента](https://github.com/Kwentin3/1c-agent-harness/issues/4)

**Результат:** один и тот же контракт исследования выполняется через Hermes/Codex CLI и ещё один совместимый агентный клиент без изменений ядра.

**Гейт:** различия ограничены адаптером или инструкциями клиента; evals используют общий набор вопросов и доказательств; абстракции для гипотетических клиентов не добавлены.

**Статус:** Antigravity canary-proven, но два frozen arm attempts упали до answer
artifact; standalone альтернативные CLI не установлены. Этап не закрыт; см.
[`docs/client-readiness.md`](docs/client-readiness.md).

## После read-only MVP

Только после прохождения предыдущих гейтов отдельно рассматриваются:

- контролируемое изменение выгрузки;
- нативная проверка и обратная загрузка;
- тестирование в изолированной информационной базе;
- runtime-диагностика;
- дополнительные способы подключения к 1С.

Эти направления не являются автоматически одобренными функциями roadmap. Для каждого требуется отдельная продуктовая цель и модель безопасности.
