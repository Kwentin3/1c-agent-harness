# Goal107: единый Harness через Hermes Relay

## Цель и границы текущего этапа

Пользователь выбирает компьютер и разрешённую 1С в обычном Hermes WebUI,
ставит предметную задачу и использует единые инструменты Harness. Hermes
планирует работу и оценивает достижение пользовательской цели; Harness
выполняет предметные операции и возвращает результаты проверок; Relay владеет
подключением, выбранным устройством, локальными разрешениями и исполнением.

Первый этап — содержательно принять существующие возможности на действующем
Linux-полигоне и перевести его рабочий маршрут на Relay с проверенным возвратом.
Windows остаётся обязательной частью полной Goal; Linux PASS не закрывает #107.
Новые функции разработки, универсальная IDE и автоматическая установка любой
1С не входят в перенос. Точечные изменения общего кода допустимы при доказанной
необходимости; отдельный транспорт, очередь, реестр устройств и ОС-форк не нужны.

Исходная source-база: Harness `0071e381f1dc0c97b5662b2e842c9cf634e493a9`,
Hermes `8ae0d19ab876b924a0b57e687573daddff1a01f0`.
Read-only сверка 23 октября 2026 подтвердила установленный plugin artifact
`sha256:b08132ccbe0fddb1a0d2199e410ea37a4f89d21b4af238503d69f906739fa1a1`
и launcher SHA256 `a4bb6f6f19dc166c56b56acd2289041963548fd913575a7f0df7a02e27e5766e`.
Это исходная опора, а не приёмка нового маршрута.

## Владельцы и контракты

| Значение | Владелец | Контракт и потребитель |
| --- | --- | --- |
| Выбранный компьютер чата | Relay/Hermes PluginState | Точный device ID, доверенный session ID, generic Relay dispatch |
| Разрешение и неопределённый исход | Relay и существующий outcome guard | Native tool result и корневой relay_outcome; потребитель Harness transport |
| Предметный запрос/результат | Harness | Закрытый JSON schemaVersion/operation/arguments; artifact/capability проверяет plugin |
| Выполнение длительной команды | Native Relay jobs | start/status/logs/cancel; адаптер не создаёт вторую очередь |
| Snapshot/task/observation/capture refs | Harness | Существующая предметная проверка плюс привязка к устройству на границе транспорта |
| Точная ИБ, контейнер, runtime и права | Существующие контроллеры полигона и deployment | Локальный stdin-вход; caller не выбирает source/path/container/user |

Обычный `PluginContext.dispatch_tool` в закреплённом Agent обходит model-tool
hooks. Поэтому нельзя полагаться на автоматическое применение выбора Relay к
вложенному вызову. Текущий launcher также содержит фиксированные SSH-переходы;
новая доставка должна доходить до локального владельца на выбранной машине.

## Делегированные срезы

| Срез | Область изменения | Приёмка |
| --- | --- | --- |
| R1 — generic Relay boundary | Только Relay agent plugin и его проверки в Hermes | Доверенный SID; точный target на каждом шаге; отказ без dispatch; unknown outcome сохраняется во внешнем результате; status/logs остаются чтением |
| H1 — Harness transport | Только plugin adapter/transport и тесты | Тот же JSON через native jobs.stdin; целый проверенный ответ; Unicode/byte bounds; отсутствие server write_file/fallback; чужой или неоднозначный ref отклоняется |
| L1 — local Linux execution | Минимальный stdin-вход existing controller и deployment adapter | Те же binding/lock/native owners; фиксированное окружение; отсутствие SSH; неподходящий контейнер/источник отклоняется до native работы |
| I1 — интеграция и поставка | Root: matched release/pins, установка, возврат | Проверен точный доставляемый артефакт; сохранён старый маршрут; конкретный список затрагиваемых объектов |
| A1 — ordinary-chat proof | Root: обычный Hermes WebUI, выбранный полигон | Реальный зарегистрированный one_c_* прошёл Relay и вернул данные нужного источника |
| A2 — Linux product regression | Root и независимый reviewer | Принятые предметные сценарии, source/result/omissions, cleanup и восстановление |

Каждый исполнитель меняет только выделенную область. Root читает артефакты,
проверяет границы и принимает результат; текст отчёта агента сам по себе не PASS.

## Содержательная опора и приёмка

Сохраняются ранее принятые сценарии из [Goal91](goal91-final.md),
[#99](issue99-agent-logging.md), [#102](issue102-access-pr-closeout.md) и
[#104](issue104-registration-recovery.md):

- configuration open, warm reuse, содержательный narrow search;
- stage разрешённого task и native verify на отдельной disposable ИБ;
- ЖР select/page/record с сопоставлением native/cache/public и честной полнотой;
- ТЖ status/start/read/drilldown/stop с восстановлением исходной настройки;
- ЖР start/stop и следующий сбор; изменённые уровни проверяются отдельно от
  уже включённых. Существующий recovery protocol не заменяется ручным state edit.

Два чата и смена выбранного устройства не перенаправляют начатую работу.
Refs другой машины, в том числе одинаковые content refs на разных устройствах,
не принимаются неявно. Offline/refusal/revoke не вызывают fallback.
После потери ответа изменение не повторяется автоматически; известные job ID,
device ID и capture refs сохраняются для штатного выяснения состояния.

Текущий срез рассчитан на один исполняющий Agent/Gateway-процесс: конфликт
привязки одинакового ref между его потоками защищён общим lock. Публичный
PluginState предоставляет get/set без межпроцессного compare-and-set;
несколько независимых Agent с общим state этим этапом не квалифицированы.

A1 не включает включение журналирования, export, новый native lifecycle или
перезапуск 1С: сначала доказывается минимальный реальный маршрут.
A2 запускается после проверки окончательного запроса на фактическом входе и
сверки актуального допуска. Исторические native-бюджеты не переиспользуются.
Исходная конфигурация и бизнес-данные остаются read-only.

## Поставка и оставшийся объём

Сначала адресные проверки границ, затем обязательный exact-head CI и ordinary
chat acceptance. Зелёные тесты и job ID не заменяют продуктовую приёмку.
Переключение полигона требует рабочего нового маршрута и проверенного возврата;
прежний доступ не удаляется в исследовательском этапе.

Для полной Goal дополнительно требуется реальная Windows-1С с согласованным
обязательным набором возможностей, воспроизводимая подготовка следующей машины
и матрица проверено/не поддержано/не проверено. Отсутствующий ресурс оформляется
конкретным blocker; сужение обязательного набора принимает владелец.
