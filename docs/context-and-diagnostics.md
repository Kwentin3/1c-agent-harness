# Контекст и диагностика: точечный рефакторинг

## Цель и границы

На действующем домашнем Linux-полигоне агент загружает необходимые инструкции
по задаче, получает первичную причину сбоя отдельно от Exit/очистки и понимает,
какую часть журнала удалось достоверно прочитать. Принятый маршрут Hermes →
Harness → Relay → допущенная 1С и существующие возможности сохраняются.

Это отдельная Goal после [Linux-этапа #107](issue107-relay.md). Windows,
изменение ограничений учебной версии, новые прикладные функции 1С и перестройка
транспорта исключены. Допуски на native-операции и перезапуски прежних этапов
не переносятся автоматически. Исходная конфигурация и бизнес-данные read-only.

## Срезы и владельцы

| Срез | Существующий владелец | Проверяемый результат |
| --- | --- | --- |
| D1: загрузка инструкций | Нативный механизм навыков Hermes | Установлена причина повторов; избыточные полные копии устранены, обоснованная повторная загрузка сохраняется |
| D2: исход ошибки | Native-адаптер и logging lifecycle Harness | Первичная ошибка, наблюдённый отказ платформы и Exit/cleanup различимы; неизвестная запись не повторяется вслепую |
| D3: полнота ЖР | Native export, capture receipt и retained selection | Гарантии временного окна установлены по нативному источнику; подтверждённая полнота имеет проверяемые условия, ограничение — воспроизводимые свидетельства |

Новые cache/registry, транспорт, очередь или самостоятельный интерпретатор
бизнес-результатов не требуются. Изменения вносятся в существующего владельца;
граничная проекция передаёт его подтверждённые факты без собственной трактовки.

## Исходная опора

Принятый runtime Harness: source `285750aa0f9eaf7e807292c91310f0447481db64`,
artifact `ef59b2358c515bd312d7b372de020925cbe36afd23e4be7829ee6018b415077a`;
matched Hermes recipe `a0a946e4da5505f7664155eb1e00bc93cb1ad3f1`.
Source/docs базы: Harness `b0ebfcca`, Hermes `efc678ed`. Новый кандидат пока
не установлен; установленная версия и source-кандидат различаются явно.

Наблюдения, а не готовые диагнозы:

- Прежний чат содержит три одинаковых полных результата `skill_view` одного
  навыка. Причина и избыточность каждого повтора требуют проверки контекста,
  native task/session identity и штатной дедупликации; сам повтор не доказывает баг.
- `RegistrationWeb._visit` заменяет исходную ошибку ошибкой завершения из
  `finally`. Сохранённый случай содержит фактический отказ учебной 1С по числу
  подключений. Исправление диагностики не означает исправления этого ограничения.
- Единственный свежий ЖР export дал 5 записей, все 5 дошли в retained и public.
  Receipt содержит `capture_consistency_unproven`; совпадение записей не является
  доказательством полной истории временного окна.

## Приёмка

1. D1: faithful reproduction использует фактический transcript и нативного
   владельца. Проверяются повтор без обновления, отдельный supporting file,
   изменение инструкции и восстановление действительно утраченного контекста.
2. D2: проверяются первичная ошибка плюс ошибка Exit/cleanup, сохранение после
   возможного Save и подтверждённый отказ без Save. Успех по-прежнему требует
   штатного завершения и положенного свежего readback. Raw UI/Playwright-тексты
   и приватные пути не подменяют ограниченный публичный диагностический контракт.
3. D3: actual native request/output сверяются с условиями API, фильтрами,
   count boundary и временной границей. Новый эксперимент сначала репетируется
   на сохранённом фактическом входе. Отсутствие доказательства полноты не
   переименовывается в доказательство невозможности или в полный результат.
4. После содержательной проверки кандидата проходят обязательные exact-head CI
   и проверка затронутого обычного маршрута в пределах свежего допуска.
   Исходники, бизнес-данные, выбранная цель и исходные настройки сохраняются.

Каждый срез делегируется с отдельной областью файлов и приёмкой. Ответственный
исполнитель читает артефакты и сводит результат; отчёт агента и зелёные тесты
сами по себе не являются приёмкой установленной версии.

## Source-кандидат D2/D3

В существующем native-адаптере первичная ошибка сохраняется отдельно от Exit
и очистки ресурсов. Ограниченный `diagnosis` доходит через прежний logging
backend до companion и предметного инструмента. Он различает прочитанное
значение, подтверждённый отказ, незавершённую операцию и неизвестный исход Save.
Подтверждение успешного запроса по-прежнему требует штатного Exit и нужного
свежего readback. Durable `prepared`/`restoring` и восстановление #104 сохранены.

`training_connection_limit` появляется только при наблюдении точных двух
маркеров в открытых подробностях нативного окна ошибки. Один timeout, общий
экран недоступности или случайный текст поля такой причины не доказывают.
Неизвестный Save не превращается в подтверждённый отказ и не повторяется вслепую.

В ЖР устранена ложная граница количества для подтверждённого экспорта `ibcmd`
без native count limit. Существующий `Capture` v1 создаётся deployment-владельцем
после проверки точного native argv, binding, exit и полных байтов результата.
Для этого пути потеря по количеству определяется как
`matched_count > maximumCount`; равенство и лишние записи вне фильтра потерей
не являются. Старый EPF-путь сохраняет консервативную оценку границы.

### Какая полнота доказуема

`retainedCountComplete` относится к полученным совпадающим записям, а не ко
всей истории интервала. [Сохранённая справка точной платформы 8.5.1.1150](../experiments/issue90-current-source/ibcmd-eventlog-help.txt)
описывает экспорт доступных событий без flush/fence/watermark. `--follow` ждёт
новые события; его значение не является сроком окончательного опустошения буфера.
Общее устройство хранения и экспорта описано в [руководстве поставщика 8.3.27](https://1c-dn.com/library/tutorials/1c_enterprise_administrator_guide_file_mode_8_3_27/);
оно не выдаётся за точную спецификацию синхронизации 8.5.1.

Для более сильного утверждения нужны подтверждение сохранности всей требуемой
истории и финализации соответствующих writers, либо отдельно определённая
область запечатанного неизменяемого persisted source. Равные stat-инвентари,
две равные выборки, дата последнего события и время получения ответа такую
финализацию не доказывают. В текущем контракте остаются
`temporalComplete=false` и `completeThrough=null`; глобальная невозможность
подтвердить полноту другими API этим исследованием не утверждается.

Изолированный Linux-прогон source-кандидата: 595 тестов, 6 предусмотренных
пропусков; адресные проверки native-адаптера, logging-проекции и ЖР также прошли.
После обновления инструкций проверен plugin boundary (27 тестов). Native 1С,
новые экспорты, установка и изменение живых настроек этим не выполнялись.
