# Правила работы кодового агента

Этот файл действует для всего репозитория.

## 1. Миссия текущего этапа

Доказать, что кодовый агент способен безопасно и воспроизводимо исследовать незнакомую конфигурацию 1С в режиме read-only. Создание полноценной среды разработки и изменение конфигураций пока не являются целью.

**Read-only остаётся режимом по умолчанию.** Явная issue может разрешить ограниченный
write-эксперимент (как issue #10). При этом:
- запись разрешается только в физически отделённую work copy и disposable test ИБ внутри `.local/`;
- исходная конфигурация, snapshot, manifest и живая ИБ остаются immutable; любое их
  изменение — стоп/провал, даже если после восстановления байты совпали;
- один доказанный Jet slice не означает универсальную write-поддержку; каждое новое
  write-изменение требует отдельной issue и своей модели безопасности.

## 2. Иерархия контекста

Перед работой:

1. прочитай `README.md`;
2. прочитай документы, указанные в issue;
3. воспринимай issue как контракт на результат;
4. проверь текущее состояние репозитория и существующие решения до написания нового кода.

Если формулировки конфликтуют, безопасность и явные ограничения issue имеют приоритет. Существенный конфликт, меняющий продуктовую цель, является точкой остановки.

## 3. Автономия

Внутри границ issue агент вправе самостоятельно:

- декомпозировать цель и менять рабочий план;
- исследовать документацию и существующие проекты;
- выдвигать и проверять гипотезы;
- выбирать или отклонять зависимости на основании эксперимента;
- реализовывать, рефакторить и удалять собственное неудачное решение;
- запускать проверки и собирать доказательства;
- обновлять документацию, если фактическое устройство проекта изменилось.

Не требуется согласовывать обратимые технические решения, которые не расширяют scope и не меняют принятые контрактные границы.

## 4. Обязательные ограничения

- Работай в предоставленном Hermes Project Workspace; до установки зависимостей проверь фактические `cwd`, Git-корень, terminal backend и персистентность.
- Не создавай дополнительную абстракцию workspace. Корень выбранной основной папки должен быть корнем репозитория.
- Машинно-локальные дистрибутивы, fixture, снимки, индексы и кэши размещай только в `.local/`, исключённом из Git.
- Не меняй глобальную конфигурацию Hermes или terminal backend без доказанной необходимости и явного описания последствий.
- Сохраняй read-only режим относительно исходной конфигурации и информационной базы.
- Используй нативные возможности платформы 1С там, где они доступны и воспроизводимы.
- Не управляй GUI и не используй скриншоты как основной интерфейс агента.
- Не создавай собственный парсер, индекс, граф, RAG или универсальную систему плагинов, пока эксперимент не показал конкретный незакрытый пробел.
- Сначала проверяй готовый инструмент как внешнюю зависимость; форк требует отдельного доказательства.
- Не допускай проникновения типов и допущений Hermes, Codex, конкретного MCP или конкретной версии платформы через доменные границы.
- Не копируй сторонний код до выбора лицензии проекта и проверки совместимости лицензий.
- Не добавляй функции для будущих сценариев, которых нет в текущей issue.

Архитектурная граница не обязана немедленно становиться интерфейсом, классом или отдельным сервисом. Для MVP достаточно минимального проверяемого контракта данных и поведения.

## 5. Доказательства

Каждый существенный вывод об исследуемой конфигурации должен содержать проверяемый locator: путь и участок файла, идентификатор объекта метаданных либо другой воспроизводимый источник.

Разделяй:

- подтверждённые факты;
- выводы, полученные из нескольких фактов;
- предположения;
- неизвестное.

Название объекта само по себе не доказывает его назначение. Если ответ нельзя подтвердить, это должно быть явно указано.

## 6. Исследование и зависимости

При затруднении не останавливайся на первом варианте:

1. установи корневую причину;
2. найди несколько реалистичных кандидатов;
3. проверь их минимальным экспериментом;
4. выбери наименьшее решение, которое достигает цели;
5. зафиксируй причины только для существенного или труднообратимого выбора.

Заявления из README стороннего проекта считаются гипотезой до проверки на нашем сценарии. Версии зависимостей и условия эксперимента должны быть воспроизводимы.

## 7. Точки обязательной остановки

Остановись и запроси решение, если требуется:

- изменить живую информационную базу или исходную конфигурацию;
- получить отсутствующие секреты, лицензии либо закрытые данные;
- принять юридически значимое решение о лицензии;
- опубликовать пакет, релиз или внешний сервис;
- совершить необратимое действие;
- существенно расширить продуктовую цель;
- продолжить без обязательной тестовой конфигурации или без возможности проверить результат.

В отчёте о блокировке укажи уже проверенные гипотезы и минимальный вопрос, без ответа на который нельзя двигаться дальше.

## 8. Готовность результата

Работа не закончена, пока:

- критерии issue не проверены фактически;
- тесты или эксперименты можно повторить из чистого окружения;
- отсутствуют необъяснённые изменения исходных данных;
- документация соответствует реализации;
- известные ограничения и неподтверждённые выводы перечислены явно.

Финальный отчёт должен описывать достигнутый результат, доказательства, принятые существенные решения, оставшиеся ограничения и способ воспроизведения. Хронологический дневник действий не нужен.
